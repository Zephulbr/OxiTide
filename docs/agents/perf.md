# Performance harness

Read before running or changing `scripts/perf/`, or when a change needs a perf measurement. Linked from `AGENTS.md`.

Track 3's measurement gate lives in `scripts/perf/` (manual; no CI):

- Windows-only exemption (Track 8, T8-D3): the scripted runner/driver (`run-scenario.ps1`, `drive.mjs`) speaks the WebView2 CDP endpoint and is not ported to WebKitGTK. On Linux the `/proc` metrics in `crates/oxitide-app/src/perf.rs` keep process-relative marks, memory, and playback rows measurable via `OXITIDE_PERF_SCENARIO` + `node scripts/perf/check.mjs`; frame/interaction budgets stay unmeasured until the deferred harness port. Authority: `docs/superpowers/plans/notes/2026-10-03-track8-perf-exemption.md`.
- `powershell -ExecutionPolicy Bypass -File scripts/perf/run-scenario.ps1 -Scenario <S1..S14> [-Runs n] [-Manual] [-SkipCheck] [-Minutes n]` — launches the debug exe (Vite must be warm; the script starts it if port 1420 is free) and drives the scenario over the WebView2 CDP endpoint. Raw JSONL lands in the gitignored `.superpowers/perf/runs/`.
  - `-Release` (Track 13) runs `target/release/oxitide-app.exe` with the UI embedded and no Vite; build it with `npm --prefix ui run app:build:perf` (`tauri build --no-bundle`; plain `cargo build --release` still points at `devUrl`). Baselines are taken on release builds.
  - Runs end through `perf_quit` (normal exit work); the runner kills the app only if it is still up 10 s later.
- `powershell -ExecutionPolicy Bypass -File scripts/perf/run-corpus.ps1 [-Scenarios S1,S2,...] [-Runs n]` runs a whole release corpus unattended (every scripted scenario by default, S12 included; S8/S9 once). It archives old JSONL out of `runs/`, keeps the display on, turns scrobbling off and restores `config.toml` / `session.json` / `history.jsonl` afterwards, kills a hung scenario at its timeout, and writes `metrics.txt` / `check.txt` to `.superpowers/perf/corpus-<stamp>/`.
- `node scripts/perf/check.mjs` (or `npm --prefix ui run perf:check`) aggregates the corpus against `scripts/perf/budgets.json` (mirrors spec §4.2) and exits non-zero on any breach. Samples carry per-process working set, private bytes and cumulative CPU ms, plus `ipc` rows (cumulative desktop `playback_event` + Rack `level_frame` count/bytes; rates are last − first, never a sum of rows); the checker derives `cpu_app_pct`, `cpu_webview_pct` (percent of **one core**), `private_max_mb`, `ipc_events_per_min`, `ipc_kb_per_min`, measured from a `measure_start` mark when the driver sets one.
  - `ipc_idle_events` counts the `playback_event`s that reach the window outside every track change: counter growth in a sample interval that does not overlap 2 s before that change's `info_ready` (or its `first_pcm`, whichever is earlier; `info_ready` at most 15 s back) to 10 s after its `first_pcm`. A transition that drains and reopens the output sends `now_playing` / `state` before its first PCM write, and a crossfade across a format change fades the old tail out for the whole crossfade first (~4 s early at a 4 s crossfade). S12 requires 0: hidden, only track changes may cross into WebView2 (position ticks and beat clocks are held, `position_feed.rs`), and its per-minute rate then depends on track length, so it is a median row of its own.
  - A budget is checked against the worst run (p95 across runs), a `min` budget against the lowest; `"of": "median"` checks the median run instead. CPU and IPC rate rows use it (they swing between runs; the S11–S14 budgets are median + 15 %, CPU at least +0.5 pt), memory and frame rows stay worst-run.
  - CPU comes from `cpu_cycle_ms` (Windows `QueryProcessCycleTime`, converted with the measured TSC rate) when every row has it, else `cpu_ms`. `cpu_ms` is Windows process time, which is sampled at the 15.6 ms clock tick and charged to whichever thread is running at the tick: per-frame bursts at 144 Hz alias with it, so identical S13 launches read 7–39 % on it while their cycle counts agreed within 1.4 % (2026-11-04). Budgets set on `cpu_ms` (S11–S14 before 2026-11-04) are not comparable with cycle-based runs.
  - `measure_start` also restarts the UI's frame and long-task samples (`__perf.resetSamples()`), and the checker drops frame and long-task rows sent before it, so start-up, a mode switch or a fixture load stays out of a steady window's frame rows (S13's 34.6 ms p99 and 105 ms long task were the switch to Rack). S14's window is a fixed 15 s from `measure_start`: its sweeps step once per display frame, so a window that ended a fixed time after them made a faster display read as higher per-minute CPU and IPC for the same 360 volume changes.
- Scenarios: S1 cold start, S2 warm start, S3-miss/S3-hit TTFS, S4 gapless advance, S5-instrument/S5-atmosphere scroll, S6 10k filter/sort/album, S7 10k queue load (end to end: command → state applied in the UI), S8 cache loop, S9 2 h soak, S10 manual stability, and (Track 13) S11 idle paused, S12 playing hidden to tray (the driver closes the window through `perf_close_window`, the close button's own close-to-tray path; close to tray must be on), S13 Rack with meters, S14 volume drag on a 10k queue. S4/S8/S9/S12 need a real account and audio (scripted), S10 is human-in-the-loop (real account/audio); the rest are scripted. S7/S14 replace the session queue with synthetic items and clear it afterwards. S4, S12 and S13 play fixed tracks (`PINNED_TRACKS` in `drive.mjs`, the ones the 2026-11-11 final corpus played), because their gaps, track changes and IPC bytes follow the music; S3/S8/S9 still take the favourites. A pinned track that TIDAL withdraws fails the run with its id: re-pin it (and re-measure the rows it feeds), or pass `--favorites` to `drive.mjs` for the old behaviour.
- `drive.mjs`'s `awaitPlaying` requires the position to advance: a session stuck paused at a restored position reports `playing` with a non-zero position, and silent runs used to be measured as playing. Check `first_pcm` rows before trusting a playback scenario.
- The UI's frame sampler is a rAF loop of its own, so it keeps the window producing frames; idle scenarios (S11/S12) switch it off through `__perf.sampleFrames(false)`. The driver also logs Chromium's page counters (`Performance.getMetrics`: style recalcs, layouts, script/task time, JS heap) and the running animations as `ui_metrics` rows with a `page` field, at `measure_start` and at the end; the checker turns them into `page_*_per_min`, `js_heap_max_mb` and `animations_max`. `check.mjs --metrics` prints every metric (median / worst run), budgeted or not.
- `advance` gaps time from the previous track's last output write of any kind (a crossfade's faded tail included), so a crossfaded or format-changing transition reports its real silence.
- Conditions matter: single app, foreground, Vite warm, no deliberate background load. `scripts/perf/budgets.json` is the source of truth for the budgets. Their history: the original budgets and the S4 documented finding in `docs/superpowers/plans/notes/2026-10-02-track3-phase-d.md`; Track 13's release-build results and the S11–S14 budgets in `docs/superpowers/plans/notes/2026-10-19-track13-perf-results.md`; the v1.0 rulings (release reference, memory = worst run + 15 %, S4/S6 handling) in `docs/superpowers/plans/notes/2026-10-23-v1-perf-rulings.md`.

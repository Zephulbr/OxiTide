# Audio engine notes

Read before touching `crates/oxitide-audio` or the playback wiring: network resilience, output backends, ASIO, DSP/AutoMix and autoplay. Linked from `AGENTS.md`.

- Network resilience in `crates/oxitide-audio` (playback's retries all come from `retry::Backoff`; `connectivity::global()` reports OS network changes — Windows `NotifyNetworkConnectivityHintChange`, Linux a 2 s default-route check — which cut waits short, and time the OS reports offline does not count toward `retry::NETWORK_LIMIT`):
  - `fetch::download_ahead` writes a whole track to disk at full speed (the cache `.part`, or a `spill-*.part` scratch file for seeked streams) while a feeder hands it to the decoder through the 2 MB `StreamBuffer`; `AheadGate` lets only the first download in line run ahead (playing track before prefetch).
  - A lost network mid-track is ridden out **in place** (`fetch_recovering`): the segment retries on `Backoff::network`, rejected/aged links are renewed through a `fetch::Refresh` closure (same manifest hash and segment count, else `FetchRejected` and the engine restarts at the position), the decoder just waits, and the worker shows `PlaybackState.buffering` while it is starved — same session, same open device. A spent backoff is `NetworkLost` (not transient).
  - Failures before any audio (resolve errors, a stale failed prefetch) end the session; the worker waits on `Backoff::network` with `buffering` set and resumes at the recorded position (a pause during the wait keeps it).
  - Committed cache entries carry a `{entry}.fmp4.meta` sidecar (URL-free `StreamPlan`); `DiskCache::find_offline` plays a cached track when `playbackinfo` is unreachable (older entries without a sidecar via `decode::probe`). Startup restores offline from `config\tidal_session.json` when TIDAL is unreachable. Two non-v1 bases exist: internal `api.tidal.com/v2` (`get_v2`, used for writes/feed/folders) and public `openapi.tidal.com/v2` (`get_openapi`, JSON:API; playlist follower counts live only there).
- ASIO output (Track 7, spec `2026-10-11-oxitide-track7-asio-output-design.md`): Windows `real_output()` is `routed_output::RoutedOutput`, which dispatches to `WasapiOutput` or `AsioOutput` by device id (`asio:<registry key>`; drivers enumerate from `HKLM\SOFTWARE\ASIO` without loading). The IASIO binding is hand-written in `asio_sys.rs` (no `asio-sys`/LLVM; 64-bit only). An `asio:` device always runs `OutputMode::Exclusive` (`output::effective_mode`) and holds volume at 100% (`PlaybackState.volume_fixed`: ASIO has no endpoint volume, so `SetVolume` is ignored and the UI disables volume controls; the saved volume returns with the next device); a failed ASIO open follows `exclusive_fallback` (WASAPI shared default + notice, or error). Picking a device moves the open output in place (`engine::switch_device`, keyed on `device_version`) unless the output mode changes, which restarts at the position; re-picking the same device (`reselect_device`) reopens it in place, so it retries after a fallback. Driver calls stay on the `oxitide-asio` owner thread; the render callback reads a process-global state, so only one ASIO driver can be open.
- Device fallback (WASAPI): a selected endpoint that is missing **or not active** (a USB DAC still waking keeps its id) opens on the system default with a `warn!` and a notice. That session watches for the selected id to be added or turn active, or for the render/console default to move, and sets `AudioOutput::needs_reopen`. The engine then restarts the track at its position (no pause, unlike device loss) and reopens at the next track start even when the wanted spec is unchanged. `open_spec` holds the *requested* id, not the opened one, so never rely on a spec comparison to leave a fallback. `Engine::set_output_device` forces a reopen too (in place in a running session, see `switch_device`), so re-selecting a device retries it. A failed ASIO open falls back to the WASAPI default and does not retry ASIO until the next reopen (ASIO has no arrival notifications).
- Output picker (spec `2026-11-05-oxitide-output-device-picker-design.md`):
  - **Devices:** `OutputDevice` carries a clean `name`, the `system_name`, `group` / `kind` /
    `transport`, `wrapper` (ASIO4ALL etc.) and `present`. `devices.rs` holds the pure naming
    rules and the `/proc/asound` parsers (spike `plans/notes/2026-11-05-device-properties-spike.md`).
  - **WASAPI** reads names, form factor and enumerator from the endpoint property store.
    `is_default` compares ids.
  - **ALSA lists one row per card + PCM** (`hw:CARD=X,DEV=n`). Shared mode opens its `plughw:`
    twin and Exclusive opens `hw:`. `sysdefault`, `plughw` and `default` are not rows, and
    saved ones migrate (`devices::migrate_alsa_id`). HDMI rows take the monitor name from ELD.
  - **Exclusive is per device:** `[audio.devices."<id>"].mode`, read with
    `AudioConfig::mode_for`; ASIO is always exclusive. `Engine::set_output(device, mode)`
    switches both with one reopen. The old global `audio.exclusive` is read once and moved
    onto the selected device.
  - **Capabilities:** `devices::probe_caps` covers WASAPI (an exclusive format sweep, 20–80
    ms), ASIO (loads the driver on its own thread, skipped while ASIO is open, 3 s cap; an
    open waits out a running check via `claim_for_open`) and ALSA (USB `stream0`, else a
    non-blocking `hw_params` look).
  - **Change notifications:** `devices::watch_devices` (Windows `IMMNotificationClient`,
    300 ms debounce) costs nothing while idle. Linux has no watcher; the picker re-reads when
    it opens or the window regains focus.
- Device fallback (ALSA, 2026-11-05): a selected device on a specific card (`hw:`/`plughw:`/`sysdefault:CARD=…`) that cannot be opened shared falls back to `default` with a `warn!` and the same notice. The session then watches that card's `/proc/asound/<id>` (one `stat` a second, `alsa_output::CardReturn`) and reports `needs_reopen` only once the card has been **gone and come back**, so a card held by another program never loops. The open that follows waits up to 7 s for the card to stop answering `EBUSY`: on PipeWire our fallback stream was routed to the returning DAC, and WirePlumber keeps the device until it suspends the idle sink (5 s by default), so the move costs a few seconds of silence. Any open right after our own stream on `default` (the user's choice too, not only a fallback) gets the same wait, and an exclusive open that still fails on a busy `hw:` device says "output device is busy …" (`DEVICE_BUSY`), never "exclusive mode is not supported". A lost device (`ENODEV`/`ESHUTDOWN`) reads "output device disconnected" (`DEVICE_DISCONNECTED`), never alsa-lib's raw text.
- ALSA transport edges (2026-11-05, L3): the buffer is ~150 ms (`buffer_frames`, 4 aligned periods: 6400 frames at 44.1 kHz) and a prepared PCM starts only at buffer minus one period (`start_threshold`; alsa-lib's 1-frame default ran dry right after every start). Every open and flush fades in over the 30 ms `GainRamp`. `write` holds back its newest 10 ms; on pause the engine calls `AudioOutput::fade_out`, which writes them faded to zero plus 10 ms of silence, so the play-out ends on silence; `drain` writes them as they are (and starts a PCM that never reached the threshold). A new session on the open device without a seek (a skip, a new context) also calls `fade_out` first, so the next track does not join the old one's buffered audio with a step. `flush` and `stop` first `settle`: on a running PCM they write the faded end and wait (≤ 300 ms) until the device has played into its silence, then drop, because the `alsa` crate exposes no rewind. Skip and seek therefore lag by up to the ~150 ms buffer. Clicks remain on `sysdefault:` (alsa-lib `plug` + `dmix`) but not on `default` (PipeWire) or direct `hw:` (2026-11-05 retest). Gapless advances keep the device, so steady playback stays sample-exact.
- Sound processing (Track 7): `crates/oxitide-audio/src/dsp.rs` (pure: `DspSettings`, RBJ `f64` biquads, ReplayGain math, crossfade `Tail`) runs in the playback worker between the producer and `output.write`. Identity settings must stay a no-op so exclusive `i32` output remains sample-exact; any stage that alters samples clears `PlaybackState.bit_perfect` and lists itself in `dsp_stages` (never in the output notice). Settings apply live via `Engine::set_dsp` (version counter, no restart), persist as `[dsp]`, and reach the engine through `set_dsp_settings`. Crossfade holds back a FIFO of decoded audio and mixes it into the prefetched next stream on natural ends only. AutoMix (Track 7b, `automix.rs`, pure Rust: `rustfft` + `rubato`) adds individually toggled silence trim, cross-format overlap, and beat matching: the prefetch stream pre-reads the next track's opening (`TrackStream.pending`), beat analysis runs on a helper thread while the tail keeps playing, and every transition publishes `PlaybackState.last_transition`. With the toggles off the Track 7 path is unchanged. Track 7b.2 adds `CrossfadeSettings.style` (`classic` / `quick` / `blend` / `auto` — Auto picks per pair from `automix::TransitionFeatures`, logged with every AutoMix transition; `dsp::MixShape` carries the curve, incl. the bass swap, into `Tail`) and a replay lab: while AutoMix is on the engine keeps the last tail + head (with ReplayGain, before EQ) in memory (`Engine::render_last_transition`), and the `automix_render` command returns `[u32 header len][JSON][WAV]` that Settings plays via a `blob:` URL (CSP `media-src`) — never written to disk. In shared mode with AutoMix on, a natural advance keeps the open device across format changes and streams a different rate through `dsp::StreamResampler` (AM-D16); long tail writes go through `write_responsive` (sliced, so transport commands act, and it feeds the level meter).
- Autoplay (plan `2026-10-26-autoplay.md`, `[playback] autoplay`, default on):
  - **Rust-side.** `crates/oxitide-app/src/autoplay.rs` is an engine subscriber. While the last queued
    track is current (repeat off), it appends 10 tracks from `track_radio` (falling back to
    `artist_radio`) and pools the rest of the 50. It skips queued and already-suggested tracks, ranks
    recent plays last, and applies `filter_playable_items`. Items carry `QueueItem::autoplay`, which
    is persisted in `session.json`. Turning it off removes the upcoming suggestions.
  - **The engine re-targets its prefetch on any mid-track queue edit** (`upcoming_key`: queue rev +
    repeat), so a track appended during the last one is gapless and can cross-fade.
  - **`PlaybackState.ended`** marks a natural end of the queue (not a pause). A fill that lands after
    the end appends and then sends `Next`.

- Volume: every `volume` (engine, config, UI, remote, hotkeys, MPRIS/SMTC) is a **slider position**, not a gain. Software scaling turns it into amplitude with `output::volume_gain`, a loudness-linear taper (`position^1.661`, i.e. +10 dB per doubling of loudness: 50% ≈ −10 dB, 30% ≈ −17 dB, 10% ≈ −33 dB; 1.0 stays exact unity). Cubic / 60 dB curves were tried and rejected: the bottom third went inaudible. The WASAPI exclusive endpoint gets the position unchanged (`SetMasterVolumeLevelScalar` applies the same taper). The ALSA hardware mixer still maps the position linearly onto raw steps.
  - **Volume is applied as samples leave for the device, never when they are queued.** The output ring (~200 ms) holds unscaled audio. WASAPI's pump (`write_frames`) and ASIO's `buffer_switch` read an `output::VolumeControl` every period and glide to it with `gain::GainRamp` (30 ms linear, so a jump never clicks; settled unity is a pass-through, so bit-perfect holds). An exclusive WASAPI stream with hardware volume (`QueryHardwareSupport`) steps the DAC's endpoint volume over 40 ms on the pump thread instead; one without it scales in software. ALSA has no ring of ours, so it ramps in `write` and its lag is the ALSA buffer.
  - The engine owns the `VolumeControl` and shares it via `AudioOutput::attach_volume`. `SetVolume` writes it immediately (the worker can be blocked mid-write for a whole packet); the worker still calls `set_volume` for status, then `apply_volume` re-asserts the engine's volume so a command that landed during that call is never undone. Never hold the `fade` lock across an output call (a test parks the worker inside `set_volume`). Configs written before the taper (no `audio.volume_tapered`) are converted on load with `output::volume_position` so the saved loudness is kept.

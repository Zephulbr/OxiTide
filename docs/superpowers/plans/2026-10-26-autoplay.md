# Autoplay — plan (2026-10-26)

TIDAL parity for v1: Settings → Playback → **Autoplay**, "Keep playing similar
content when your queue ends." When the last queued track is playing, OxiTide
appends similar tracks so playback carries on, gapless and with crossfade/AutoMix
where those are on.

## Research findings

- **Similar-track source already exists.** `TidalClient::track_radio(id)`
  (`tracks/{id}/radio`, 50 tracks, videos dropped) and `artist_radio(id)` in
  `crates/oxitide-tidal/src/discovery.rs`, wiremock-tested, with commands
  `get_track_radio` / `get_artist_radio`. The UI uses them for "Track radio"
  (`ui/src/lib/radio.ts`). No new TIDAL endpoint is needed.
- **Unverified:** which endpoint the official client calls for autoplay (track
  radio of the last track, or a multi-seed/mix call). Public docs and the
  reverse-engineered libraries (tidalapi, minim) do not list an autoplay
  resource. Task 0 checks this. Track radio is the fallback, and it already works.
- **Queue end lives in the engine.** `Queue::peek_next_index` returns `None`
  at the end with repeat off. `run_session` then drains and returns
  `SessionOutcome::QueueEnded` (`engine.rs` ~2917), which stops the output.
- **Gap problem: the prefetch is chosen once per track.**
  `start_prefetch` runs only when a track starts (`engine.rs` 2152 / 2206 /
  2911). A track appended while the last track plays has no prefetch, so the
  advance is a cold `start_track`. That means a gap, no crossfade, and no
  AutoMix head. The same gap happens today with "Add to queue" or "Play next"
  on the last track. A stale prefetch is already handled: it is dropped at the
  advance. A missing one is never started.
- **Content blocking is enforced server-side** by `filter_playable_items`
  (`commands.rs:1532`). Autoplay picks must go through it.
- **App-layer engine subscribers** (`commands.rs` 512–572: session saver,
  scrobbler, history, remote) are the place for an autoplay driver. It runs
  while the window is hidden to the tray or the WebView is idle, and when the
  phone remote is the only controller. A UI-driven version would not.
- **Play source** (`ui/src/lib/playSource.svelte.ts`) credits only the ids the
  source queued, so appended tracks already drop the "From …" line. Autoplay
  can label them itself.

## Design decisions

| # | Decision |
|---|----------|
| AP-D1 | The driver is Rust: `crates/oxitide-app/src/autoplay.rs`, an engine subscriber. No UI involvement in when to fill. |
| AP-D2 | **Fill ahead, not after the end.** Trigger when autoplay is on, repeat is `Off`, the queue is non-empty, and the current item is the last one (no `peek_next`). This covers the state as soon as the last track starts, and also a resume or seek onto it. It never triggers with repeat All/One (TIDAL behaves the same). |
| AP-D3 | **Seeds:** track radio of the last *user-queued* track. If that is empty, 404 or forbidden, use artist radio of its first `artist_refs` entry. If both fail, the queue ends as it does today; the failure is logged and no toast is shown. |
| AP-D4 | **Batch and pool.** Append 10 tracks and keep the rest of the 50 in an in-memory pool for the next refill, which then needs no request. Refills seed from the latest autoplay track once the pool is spent, which allows gentle drift. The pool is dropped when the queue is replaced (`PlayTracks` / `PlayShuffled` / `Clear` / restore). These are detected because the current item is no longer the one the pool was built after, or the queue no longer holds the autoplay items. |
| AP-D5 | **Dedup:** drop candidates already in the queue, picked earlier in this autoplay run, or among the last ~200 `history.jsonl` track ids (bounded read through `history.rs`). Drop tracks that are not stream-ready. Then apply `filter_playable_items`. |
| AP-D6 | **Mark items:** add `#[serde(default, skip_serializing_if = "is_false")] pub autoplay: bool` to `QueueItem`. It survives reorder, session restore and the phone remote. It is mechanical across about 34 Rust literals (same rule as `artist_refs`/`album_id`), plus `api.ts`. |
| AP-D7 | **Engine: refresh a missing or stale prefetch** when the queue changes mid-track (AP-T2). It is generic, so it also fixes the existing "Play next on the last track" gap. |
| AP-D8 | **Late fill.** If the fetch lands after the queue already ended (short last track, slow network), append and resume from the first appended item. The engine needs to tell a natural end from a user pause, so add `PlaybackState.ended: bool`: set at `QueueEnded`, cleared on any play, queue replace or seek. Next on the last track while a fill is in flight waits for it (one pending advance, with a timeout of about 5 s). |
| AP-D9 | **Toggle off** prunes the upcoming autoplay items after the current track, the way TIDAL drops its suggestions. It reuses the `plan_prune` pattern from content blocking. The current track keeps playing. |
| AP-D10 | **Setting:** `[playback] autoplay`, default **on** (TIDAL parity). Command `set_autoplay` is a sync config writer and goes in `SYNC_COMMANDS`. It is classified `NOT_EXPOSED` in `remote/rpc.rs` (the phone has no settings UI). Default on confirmed by the owner (2026-10-26). |
| AP-D11 | **Offline:** do not fetch while `connectivity::global()` reports offline. Retry once when the connection returns if the last track is still current. Never fill from the offline cache. |

## Status (2026-10-26)

Tasks 1–9 are done. The owner smoke passed (all 14 items, including the S4 perf run:
`notes/2026-10-26-autoplay-smoke.md`). The gates pass:
`cargo test --workspace`, `cargo clippy --workspace -- -D warnings`, svelte-check, vitest.

Where the build differs from the tasks below:
- **AP-D8:** Next on the last track does not wait for a fill that is still loading. The fill
  starts as soon as the last track does, so the suggestions are normally queued long before
  anyone presses Next. A Next that beats them stops the queue (no `ended`), as it does today.
- **AP-D11:** failed fills are not pre-empted while offline. A failure while the OS reports
  offline waits on `connectivity` (up to 10 min) and then tries once more. Any other failure
  retries on a later state event after 60 s.
- **Task 6:** the toggle has its own "Queue" section on the Playback tab (`list-music` icon,
  settings-search entry `autoplay`). The rail's eyebrow reads "Autoplay" without a seed
  name. There is no Settings component test (Settings has no test harness).
- **Task 7:** the phone queue is paged and can't find the first suggestion, so each
  suggestion's artist line starts with "Autoplay ·".

## Tasks

### Task 0: confirm the official endpoint (15 min, owner + browser)
Open TIDAL web (listen.tidal.com) with DevTools → Network. Play the last track
of a short album with Autoplay on. Record the call made near the end (path,
params, single or multiple seeds) in
`docs/superpowers/plans/notes/2026-10-26-autoplay-endpoint.md`. If it is not
`tracks/{id}/radio`, add a client method in `discovery.rs` with wiremock tests
and swap it in for AP-D3. Everything else stays the same.

2026-10-26: TIDAL's DataDome check blocked an automated (DevTools-driven)
browser ("You have been blocked"), so this needs a human-driven session. Do not
try to get around the bot check. A sign-in attempt by the owner in the same
DevTools-enabled browser was blocked too.

**Status: skipped (2026-10-26).** Autoplay ships on `tracks/{id}/radio`
(AP-D3). Revisit only if someone captures the official call from a normal
browser (F12 → Network, or a HAR file); then only the seeding step changes.

### Task 1: `QueueItem.autoplay` (audio + app + UI types)
- `queue.rs`: the field plus a serde round-trip test (a missing field reads as false, and false is not written).
- Update every Rust `QueueItem { … }` literal, and `api.ts`'s `QueueItem`.
- `session.rs` / `stored_ref.rs`: persisted, so a restored session keeps the label. `history::StoredRecord` does not need it.

### Task 2: engine prefetch refresh (AP-D7)
**Status: done (2026-10-26).** `upcoming_key` (queue rev + repeat) is checked
per pass while the tail is not final. Tests:
`a_track_enqueued_during_the_last_track_is_prefetched`,
`play_next_retargets_a_stale_prefetch`, `a_track_enqueued_mid_track_is_crossfaded_into`.
All three fail with the refresh disabled. The S4 perf rerun is still owed (Task 8).
- In `run_session`, remember the `queue_rev` seen at the last prefetch decision. On each loop pass where it moved, compare `upcoming_track(inner)` with `prefetch.item.track_id`. If they differ and the crossfade tail or AutoMix planning has not started, drop the old prefetch and `start_prefetch`. Once the handoff has begun, leave it (the advance already handles a mismatch).
- Keep it cheap: one atomic rev read per pass. The queue lock is taken only when the rev moved.
- Tests (`engine.rs`, `NullOutput`): (a) enqueue during the last track → the advance uses the prefetched stream (no second resolve at the boundary, no `stop`/reopen in `calls()`). (b) With crossfade on, enqueue mid-track → the transition is reported as a crossfade. (c) Enqueue after the tail started → no panic, a clean advance.

### Task 3: `PlaybackState.ended` (AP-D8)
- Set it on `SessionOutcome::QueueEnded`; clear it in `PlayTracks`/`PlayShuffled`/`RestoreSession`/`PlayPause`/`Seek`/`Next`/`Clear`.
- Add it to the desktop `StateDto` and `api.ts` (the UI can ignore it).
- Test: a natural end sets it; pause does not.

### Task 4: `autoplay.rs` driver
- `AutoplayState` on `AppState`: enabled flag, pool, picked ids, the seed, and an in-flight guard (one fetch at a time; a stale result is discarded when the queue's identity changed meanwhile).
- `on_engine_event(&EngineEvent)`: evaluate AP-D2 on `State` events and spawn the fetch on the tauri async runtime. Return at once when it is off or nothing qualifies. This is a hot path, so no locks beyond the flag check.
- Fill: seeds (AP-D3) → dedup (AP-D5) → `filter_playable_items` → `EngineCmd::Enqueue` with `autoplay: true`. If the state reads `ended` (AP-D8), also start playback at the first new index.
- Pure helpers (`should_fill`, `pick_batch`, `prune_plan`) are unit-tested without an engine. Fetch paths use wiremock and never touch live TIDAL.
- Register it as a subscriber next to history/remote in `commands.rs` (~560), and re-apply it to an engine rebuilt after re-login, as `set_beat_tracking` does.

### Task 5: setting + command
- `config.rs`: `PlaybackConfig { autoplay: bool }` under `[playback]`, `#[serde(default)]`, with a config round-trip test.
- `commands.rs`: `set_autoplay(enabled)` writes the config, updates `AutoplayState`, and prunes on off (AP-D9). Add it to `generate_handler!`, `SYNC_COMMANDS` (reason: config writer) and `NOT_EXPOSED`.
- Include it in the settings payload the UI already reads.

- Tests: the Settings toggle invokes `set_autoplay`, and the queue divider renders once and only before autoplay items (jsdom).

### Task 9: owner smoke (`notes/2026-10-26-autoplay-smoke.md`)
1. Album, last track: autoplay items appear during the track, the advance is gapless, and with crossfade on it crossfades.
2. Short last track on throttled network: the late fill resumes playback.
3. Next on the last track: it advances into autoplay.
4. Repeat All/One: no autoplay.
5. Explicit block on: no explicit picks.
6. Toggle off mid-autoplay: upcoming suggestions removed, the current track continues.
7. Restart the app: the restored queue keeps the "Autoplay" divider.
8. Hidden to the tray: the queue still extends.
9. Offline at the last track: the queue ends quietly. Online again: it fills.

## Out of scope
Autoplay for videos, "Autoplay off for this session" in the queue panel (a
possible follow-up), and seeding from the whole queue's taste profile.

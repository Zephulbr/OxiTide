# v1.0 retro: testing and release protocol

- **Date:** 2026-11-11 (after `v1.0.0` was published)
- **Status:** Changes landed; the v1.0.0 perf corpus is pending (see "Open").
- **Scope:** what the 1.0 release showed about the gates, the tests and the sign-off habits, and
  what changed before V2 work starts. Release gate: `2026-10-17-v1-release-gate.md`.

## What happened

1. **v1.0.0 was tagged on a red commit.** CI run `43065892658` on `d017cdc` failed (Linux, Rust
   tests: `trim_silence_without_silence_matches_the_plain_overlap`). `release.yml` checked only the
   version, so the release run (`43068409933`) built and drafted it anyway; `docs/release.md`'s
   "wait for CI to pass" was not enforced. Red had become routine: of the last 40 CI runs on
   `main`, 17 passed, 14 failed, 9 were cancelled. Every failure since 2026-11-07 was an
   `oxitide-audio` engine test.
2. **The perf re-run against the tagged commit has no record.** The release gate (§4) was marked
   done at 19:59 on 2026-11-11, 47 minutes after the tag (`d017cdc`, 19:12). A full corpus takes
   5–6 h. The newest corpus on disk was `corpus-20261111-144938` (the S13 A/B, finished 15:03), and
   the release exe on disk was still the 04:32 build of `a332ed2`. So `0aabe08` (exclusive fixed
   volume: audio, output and UI) shipped unmeasured. The gate already said "No corpus id or check
   output was recorded with it".
3. **Bulk sign-offs.** Four gate items were passed "as a whole" (feature smokes, the ten §3b rows,
   the profile editor with no checklist, the perf re-run). That is the owner's call for smokes, but
   the perf item is a machine record and its tick carried no id.

## The flaky engine tests

Six tests failed on CI across seven runs (2026-11-07 → 11-11). Every one runs the real engine
worker against wall-clock time, and every failure was the test's timing, not the engine:

| Test | CI message | Cause | Fix |
|---|---|---|---|
| `beat_tracking_sends_a_clock_for_the_playing_track` | first window at 1000 / 859 ms | Unpaced output: the 2 s fixture played out in ms. Either both windows were submitted before the newly spawned beat thread took the first (the analyzer slot is single, latest wins, by design), or the decoder never got ahead, so the first window started where audio was finally queued. | Paced at about real time. |
| `trim_silence_without_silence_matches_the_plain_overlap`, `resample_keeps_the_shared_device_across_a_rate_change` | 10k–43k samples too many | `play_to_end` / `play_rate_change` (and the two format-change tests) wrote at 3 ms per buffer (~30x real time). A crossfade overlaps only the tail queued ahead when the track ends; a debug-build decoder on a loaded runner fell behind, so the overlap came out short. | `TRANSITION_PACE` (about real time; 2x still fell short under the stress probe). |
| `seek_restarts_at_the_requested_offset` | `assertion failed: state.playing` | Unpaced: the second left after the seek played out before the read. | Paced at about real time. |
| `retry_after_a_stream_error_restarts_the_current_track`, `device_loss_does_not_retry_opens_while_gone` | "did not resume playback" | Unpaced (and `DisappearingOutput` / `DeviceLostOutput`): the track ended between the first samples and the `playing` read. | Paced at about real time. |

Underneath them all, `wait_for` gave up **silently** after 5 s, so a slow runner failed on the next
assert with a message naming the wrong cause. It now fails at its caller's line after 30 s (a
ceiling only). The rules are in `docs/agents/audio.md`.

Making it fail loudly found four tests that had passed by timing out:
`asio_holds_volume_at_unity_and_the_user_volume_returns`, `a_sleep_fade_on_asio_ramps_from_unity`,
`exclusive_on_a_device_with_its_own_volume_plays_at_unity` and
`a_sleep_fade_on_a_fixed_output_fades_from_unity` waited for `NullOutput::samples()`, but
exclusive and ASIO playback write integer samples (`i32_samples()`). The wait could never succeed,
so each spent 5 s and then checked things that did not need playback to have started. They now
wait on either (`wrote_audio`), which makes the suite faster: 19.7 s against 22.6 s.

`beat_engine` and other unpaced helpers stay as they are: their users do not read state that
depends on the track still playing, and none failed on CI.

Locally, before the fix: `beat_tracking…` failed in 1 of 1 full `cargo test --workspace` runs and
1 of 8 `-p oxitide-audio` runs. After: see "Verification".

## What changed

- **Release gate in CI:** `release.yml` runs the whole CI workflow on the tagged commit (job
  `gates`, `ci.yml` via `workflow_call`) before building anything.
- **Flaky tests are visible, not silent:** CI runs `cargo nextest run --profile ci`
  (`.config/nextest.toml`: two retries, no fail-fast, a hang killed after 5 min) plus
  `cargo test --doc`. A test that passes only on a retry is a "Flaky test" warning on the run and
  in its summary.
- **Toolchain pinned:** `rust-toolchain.toml` says `1.99.1`; CI and the release build read it from
  there. Bump deliberately.
- **CI coverage:** `scripts/perf/check.test.mjs` (34 tests) now runs next to the release script
  tests; pushes to `release/**` (the planned 1.x line) run CI.
- **Dependency audit:** `.github/workflows/audit.yml`, weekly and on lockfile changes: `cargo audit`
  (accepted advisories in `.cargo/audit.toml`) and `npm audit --omit=dev`.
- **Docs:** `docs/release.md` pushes the tag to the GitHub remote by name (in the owner's clone
  `origin` is Codeberg), makes it annotated from the start, and records evidence ids (step 5).
  `AGENTS.md` Workflow: notes carry a `**Status:**` line (the `DONE-` prefix is historical); a
  machine-record item is ticked only with its id; nothing a doc depends on lives only in
  `.superpowers/`.
- **Perf harness:** `run-corpus.ps1` deletes its `state-backup/` (history and config, the Last.fm
  key included) once the restore is verified by hash. It used to keep every one, and logged
  "restored" even when the hash check had failed three times. It keeps the corpus's raw JSONL in
  `corpus-<stamp>/runs/`.
- **Smoke helpers** moved from `.superpowers/` into `scripts/smoke/` (net toggle, cache and log
  watchers, glide probes), with the hard-coded user path removed.

## Verification

On the owner's machine (Ryzen 7 5700X3D, 16 threads), Rust 1.99.1:

- Gates: `cargo fmt --check`, `cargo test --workspace` (528 + 451 + 2 + 267 passed, 3 ignored),
  `cargo clippy --workspace -D warnings`, `cargo test --workspace --doc` (no doctests yet; the step
  works), both `node --test` suites (34 + 12), `cargo audit` (0 unignored vulnerabilities).
  `npm --prefix ui run check` and `npm --prefix ui test` (1377) passed before the change and the
  UI is untouched.
- The CI test step itself (the `run:` script from `ci.yml`, in Git Bash): `cargo nextest run
  --workspace --profile ci` ran 1248 tests in 16.6 s, all passing. Its flaky-test reporting was
  checked on synthetic nextest output: one deduplicated `::warning` and a step-summary entry.
- `oxitide-audio`, 10 runs while `cargo install cargo-nextest` compiled alongside: 0 failures
  (before the fix: 1 of 8 runs failed on an idle machine).
- **Stress probe** (three test binaries at once, ~3x oversubscribed; far heavier than CI): none of
  the six CI flakes recurred in 54 process runs. The probe still trips a different handful of
  wall-clock tests each batch (0/18 in one batch, 5/18 in another: a 150 ms fade stalled
  mid-ramp, a prefetch not ready on the 2 s fixture, cache fetch counts). That is the limit of
  wall-clock tests; CI's retries report such a case as flaky. The cure is the test clock under
  "Open".
- **On GitHub** (push of `799775a`): CI run `43084529189` **passed**, the first green `main` run
  since 2026-11-10 (`e9293e2`'s run `43073457027` had failed too). Toolchain 1.99.1 read from
  `rust-toolchain.toml`. nextest: Linux 1241/1241 in 46 s, Windows 1248/1248 (3 skipped) in 48 s,
  no retries, no flaky warnings. Doctests, clippy and the Node scripts job passed. Audit run
  `43084528970` passed (cargo audit + npm audit `--omit=dev`). Not yet exercised: `release.yml`'s
  `gates` job, which runs only on a tag push. The next release tag is its first run.
- Found on the way: `cargo clippy --all-targets` fails on old lints in test code
  (`needless_borrows_for_generic_args` in `oxitide-tidal` tests, possibly more behind them). CI
  lints only non-test targets, so this is not a regression. Turning on `--all-targets` would need
  a clean-up pass first. **Done 2026-11-11:** the 22 warnings (all in test code: 10
  `len() > 0`, 6 `field_reassign_with_default`, 6 one-offs) are fixed, and CI, `AGENTS.md`,
  `README.md` and `docs/linux-build.md` run clippy with `--all-targets`. Linux-only test code
  could not be linted locally (no WSL); CI's Linux job is its first check.
